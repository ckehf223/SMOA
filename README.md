# SMOA

## Spring Boot 웹 개발과 운영 배포

- IntelliJ에서 저장소 루트의 `settings.gradle`을 Gradle 프로젝트로 열고 JDK 21을 사용합니다. 서버 진입점은 `backend/src/main/java/com/smoa/SmoaApplication.java`이며 화면 소스는 `frontend/`에 있습니다.
- 루트에서 `./gradlew :backend:test :backend:bootJar`를 실행하면 프론트엔드를 포함한 실행 JAR가 `backend/build/libs/`에 생성됩니다. Windows에서는 `gradlew.bat`를 사용할 수 있습니다.
- `main` 푸시 시 [SMOA 배포 워크플로](.github/workflows/smoa-deploy.yml)가 테스트와 빌드를 실행하고 통과한 버전을 데이터스케일 서버에 배포합니다. GitHub의 Actions 탭에서 결과를 확인할 수 있습니다. 풀 리퀘스트는 테스트와 빌드를 실행합니다.
- DB 접속 정보와 운영 설정은 서버에서 관리합니다. SSH 배포 키와 서버 호스트 키는 GitHub Actions의 `production` 환경 시크릿에 저장합니다.

## 이전 Node.js 메모리 모드 참고

기존 SMOA 4.0.41 업무를 웹으로 옮기는 중간 단계입니다. 순수 HTML·CSS·JavaScript 화면과 Node.js 서버(Node 24 이상)로 구성되며, **로컬 메모리 모드**에서만 동작합니다. 업무 화면 20개와 관리 화면 4개가 실제로 동작하지만, 기존 앱과 완전히 같은 기능은 아니며 운영 배포 준비도 되어 있지 않습니다(아래 "알려진 차이" 참고).

- 자료는 서버 프로세스 메모리에만 있고 종료하면 사라집니다. DB 연결·스키마·배포 설정은 이 단계에 없습니다. DB 연결이 필요한 설정에서 메모리 모드로 자동 전환하는 동작도 없습니다.
- 서버는 `127.0.0.1`에만 열리며 다른 Host 헤더는 거부합니다.
- 모든 자료와 계정은 가상입니다. 실제 자료·연락처를 넣지 마세요.

## 실행

```
npm install      # exceljs 외에 기존 엑셀 처리용 @xmldom/xmldom, jszip, officecrypto-tool도 함께 설치됨
npm run dev      # http://127.0.0.1:3000 (파일 변경 시 재시작, 자료는 초기화됨)
npm start        # 재시작 없이 실행. 포트 변경: node server/index.js --memory --port=3100
npm test         # node:test, 모두 메모리 안에서 실행 (외부 접속·DB 없음)
```

`--memory` 플래그를 명시해야 서버가 시작합니다.

### `server/legacy` — 이식한 4.0.41 알고리즘

`server/legacy/*.cjs`와 `ui/person-milestones.js`는 기존 SMOA 4.0.41의 자료 모델·검증·집계·가져오기 알고리즘의 **순수 모듈을 이 저장소로 복사한 것**입니다(`package.json`이 `commonjs`로 지정). 웹 서버는 `createRequire`로 이 모듈을 불러 같은 규칙으로 검증·집계합니다. 기존 앱의 소스·자료·EXE는 변경하지 않았고(읽기만 함), 이 폴더 안의 복사본은 웹 이관 중 필요하면 최소한으로 조정될 수 있습니다. 서버 전용 모델 쪽에도 범위 확인을 위한 최소 검증이 있을 수 있으니, 알고리즘을 바꿀 때는 원본과의 차이를 남기고 먼저 상의하세요.

- **화면(브라우저 JS)을 바꾸려면**: `public/assets/`의 해당 화면 파일을 고칩니다(예: 콜링 통계 → `calling.js`, 활동 기록 → `records.js`, 공통코드 관리 → `admin.js`). 새 화면은 모듈에서 `{ 화면ID: 함수 }`로 내보내고 `operator.js`의 import와 `views`에 추가합니다. 화면은 DOM 노드로만 그리며(`h()`), 자료는 항상 API로 받고, 쓰기·내보내기 버튼은 `me.perms.<화면ID>`가 허용할 때만 보입니다.
- **API를 바꾸려면**: `server/`의 해당 라우트 파일을 고칩니다(예: 목표 → `organization.js`, 설정·공통코드 → `admin.js`). 모든 라우트는 `screen`과 `action`(`read`/`write`/`export`)을 선언해야 하며(시작할 때 `validateRoutes`가 확인), 자료는 `scopedWorkspace(store, user)` 복사본으로만 읽고 `commitWorkspace(store, user, draft)`로만 저장합니다. 관리자 설정 경로(단계·공통코드)는 `applyCanonical`로 복사본을 고치고 검증한 뒤 교체합니다.
- **새 화면 추가 순서**: `server/permissions.js`의 `SCREENS`에 선언 → 서버 라우트 파일 작성(`app.js` 상단 import와 `all`에 등록) → 화면 모듈 작성 → `operator.js`에 연결. 새 화면은 비관리자 기본 권한이 "접근 없음"입니다.

### 업무 자료 흐름 (`server/domain.js`)

- 원본은 `store.workspace` 하나입니다(4.0.41 호환 작업 영역: 대상자·활동·콜링·소셜링·일계·찾기 일보·목표·조직·단계·변경 이력).
- `scopedWorkspace`는 분리된 복사본을 돌려줍니다. 관리자는 전체, 그 밖의 사용자는 배정 구역(`scopeFor`)의 자료만 담깁니다. 구역 표시가 없거나 배정 밖인 행·이력은 담기지 않고, 다른 구역 구성원(인도자)은 빈 값으로 가려지며, 연락처는 끝 네 자리만 남습니다.
- `commitWorkspace`는 동기로 동작합니다. 사용자 범위 밖의 행·참조, 단계·공통코드 변경, 비관리자의 조직·소셜링 모임 변경을 거부(403)하고, 초안을 만든 뒤 원본이 바뀌었으면 409, 4.0.41 검증 오류는 400으로 돌려줍니다. 변경 이력은 원본 해시 사슬에 다시 이어 붙이고 작성자는 로그인 사용자로 고정합니다.
- 웹 단계 ID `s1`~`s8`은 고정된 기존 단계(찾B·콜링·만픽·찾A·합 B·복음방·신카접수·센터등록)에 대응하고, 이름은 `workspace.stageNames`(공통코드 관리에서 수정)가 정합니다. 구역 `d1`~`d3`은 같은 ID의 조직 노드와 연결됩니다.

날짜(등록일 기본값, 이번 달 집계, 내보내기 파일명)는 한국 시간(Asia/Seoul) 기준이며, 변경 시각은 ISO(UTC)로 기록합니다.

## 현재 변경 내용 (기존 SMOA 화면·동작 이관)

현재 저장소에 있는 파일 기준이며 기존 앱과 완전히 같다는 뜻은 아닙니다. 남은 차이는 "이관 대기·알려진 차이"에 있습니다.

- **로그인 화면**: 기존 앱의 색과 구성(소개 영역과 로그인 카드)을 옮겼고, 화면 표시 설정을 로그인 화면에서도 바꿀 수 있습니다. 로그인 처리와 세션은 서버가 그대로 맡습니다.
- **화면 표시 설정** (`theme.js`, `theme.css`): 색상 테마 4가지(청량한 블루, 차분한 그린, 따뜻한 샌드, 데이터 저널)를 라이트·다크로 바꿔 모두 8가지 조합이고, 밀도는 표준·여유·촘촘 3가지입니다. 기존 앱과 같은 키 3개를 이 브라우저의 localStorage에 둡니다.
  - `smoa-design-v2`: 색상 테마
  - `smoa-density`: 밀도
  - `smoa-theme`: 라이트·다크
- **왼쪽 메뉴**: 기존 메뉴 트리와 "메뉴 관리"(그룹 추가·삭제, 이름·순서·상위 그룹·표시 여부, 기본 메뉴 복원)를 옮겼고 사이드바 색은 선택한 테마를 따릅니다. 구성은 이 브라우저의 localStorage(`smoa-menu-tree`, `smoa-menu-open`)에만 저장하고 서버로 보내지 않습니다. 그릴 메뉴는 항상 서버가 허용한 화면과 교집합이며, 숨기거나 옮겨도 접근 권한은 바뀌지 않습니다. 저장 키에는 로그인 아이디를 소문자로 정규화한 문자열을 쓰므로 서버를 다시 시작해도 같은 브라우저에서 같은 계정의 구성이 유지됩니다. 로그인 상태는 저장하지 않으며 서버 권한 검사가 우선합니다. 관리 화면(`/admin`)은 묶음 없는 단순 목록입니다.
- **대시보드**: 기존의 한 장짜리 카드 배치를 새 대시보드로 바꿨습니다. 기간 필터와 단계별 건수, 일별 찾기 흐름, 주·월별 추이, 반별 단계 실적과 향상률, 활동자율, 지역활동기록, 구역별 목표까지 남은 건수, 단계별 목표 달성을 보여 줍니다. 모든 집계는 서버가 배정 구역 범위로 계산합니다.
- **대상자 상세**: 대상자 선택 옵션과 상세 화면, 단계 경과 기록, 삭제를 제공합니다. 기존 한 카드 안의 단순 선택 옵션은 대체되었습니다. 쓰기는 `people` 쓰기 권한과 배정 구역 안에서만 됩니다.
- **구역·반 목표**: 직전 기간 목표 복사(복사·덮어쓰기·기존 유지·제외를 미리보기로 확인한 뒤 한 번에 저장)를 지원합니다.
- **조직·구성원**: 조직·구성원 엑셀 가져오기(미리보기 후 적용)를 지원하며 관리자 전용입니다.
- **지역활동기록**: 엑셀 가져오기(미리보기 후 적용)와 내보내기를 지원합니다.
- **일보 변환·분석**: 구역별 일보 원문을 기존 앱의 경계 순서로 합쳐 변환하고, 찾기 행 검토, 행 형식 지정, 변환 결과 엑셀을 제공합니다.
- **비밀번호가 걸린 누적 엑셀**: 변환 결과를 사용자가 올린 누적 엑셀에 반영해 내려받습니다. 올린 파일에 이미 있는 내용은 기존 앱의 누적 모듈 규칙대로 보존하며, 열기 비밀번호는 요청 처리 중에만 메모리에 두고 저장·기록하지 않습니다. 업로드는 최대 8 MiB입니다. 비밀번호 파일의 처리는 `officecrypto-tool` 설치가 필요합니다.
- **관리자 기능 경계**: 사용자·접근 권한·공통코드·설정과 조직·구성원 쓰기는 관리자만 합니다. 비관리자는 화면별 접근·읽기·쓰기·내보내기 권한과 배정 구역 안에서만 자료를 보고 바꾸며, 모든 라우트는 `screen`과 `action`을 선언하고 집계·내보내기 전에 배정 구역을 적용합니다.
- **빈 자료와 빈 양식**: 자료가 없을 때 각 화면은 빈 상태 안내를 보여 주고, "엑셀 · 자료 가져오기"에서 구역 일보 정리본 등 빈 양식을 내려받을 수 있습니다. 실제 DB 초기화는 이 단계에 없습니다.

## 구현 범위

- **인증**: 공개 가입 없음. 관리자가 계정 추가·활성/비활성·역할/구역 변경·비밀번호 설정/재설정. scrypt 해시, 서버 세션(유휴 30분·절대 8시간), HttpOnly·SameSite=Strict 쿠키, 로그아웃 시 세션 폐기, 로그인 실패 제한, 변경 요청의 Origin·JSON 검사. 기본 관리자와 본인 계정의 비활성화·역할 변경, 마지막 활성 관리자 제거는 막습니다. 권한·구역·활성 상태는 요청마다 다시 읽어 접속 중인 세션에 바로 적용합니다.
- **관리 화면 (`/admin`)**: 사용자 관리, 접근 권한 관리(역할별·화면별 화면 접근/읽기/쓰기/내보내기), 공통코드 관리, 설정.
  - 공통코드: ① 대상자 단계(이름 변경·추가·사용 안 함, ID 유지) ② 코드 그룹·항목(반·직업 구분·직책·활동 종류·활동 장소 및 사용자 추가 그룹). `server/legacy/codes.cjs` 규칙을 그대로 씁니다: 코드값은 만든 뒤 바뀌지 않고, 표시명을 바꾸면 이전 표시명이 별칭으로 남으며, 기존 기록·구성원·목표가 쓰는 항목은 삭제가 거부되어 "사용 안 함"(보관)으로 전환합니다. 기본 그룹은 삭제·보관 불가이며 변경은 변경 이력(`M.audit`)에 남습니다. API: `GET /api/admin/codes`(`stages`, `groups`), `…/codes/groups[/:id[/items[/:itemId]]]`.
  - 설정: 사이트 이름과 **주 시작 요일**(0=일 … 6=토, 기본 0). `PUT /api/admin/settings`는 보낸 항목만 검증해 바꾸며(하나만 보내도 다른 설정은 유지), 저장한 값은 활동 기록·통계의 주간 집계(`weekStart`)에 쓰입니다. 요청의 `weekStart` 쿼리가 있으면 그 값이 우선합니다.
- **업무 화면 (`/`)**: 20개 화면이 모두 실제 API와 연결되어 있습니다.
  - 현황·대상자: 대시보드, 대상자 관리(검색·등록·수정·내보내기)
  - 콜링·소셜링: 콜링 관리·통계, 소셜링 관리·통계
  - 일보·활동: 일보 변환·분석, 엑셀·자료 가져오기, 활동 기록, 지역활동기록
  - 통계·분석: 단계 이동 분석, 찾기·주관자 통계, 구역별·개인별·반별 데이터, 통계 진단, 단계 강약 분석
  - 기록: 변경 이력
  - 조직·목표: 조직·구성원, 구역·반 목표

  메뉴와 가능한 동작은 서버(`/api/me`)가 결정하고, 모든 API는 중앙 가드와 구역 범위로 다시 검사합니다. 각 화면의 상세 동작과 4.0.41과의 일치 정도는 화면별로 다르므로 아래 "알려진 차이"를 함께 확인하세요.
- **엑셀 내보내기**: ExcelJS 4.4.0으로 `.xlsx` 생성. 현재 검색 조건과 같은 구역 범위만 포함하며, 연락처 정보는 이 화면 자료에 없습니다. `=`, `+`, `-`, `@`로 시작하는 문자열은 앞에 `'`를 붙여 수식 실행을 막습니다.
- 대상자 식별번호는 비우면 자동 부여(`P-0025` 형식)되며, 네 자리 숫자만으로는 만들 수 없습니다.

- **조직·구성원 화면**: 조직 계층(들여쓰기 표)과 구성원 목록·검색, 조직·구성원 추가/수정/삭제, 책임자 지정, 구성원 반 일괄 지정, 엑셀 내보내기. 비관리자는 배정 구역의 하위 조직과 필요한 상위 조직(참고용)만 보며, **쓰기는 관리자 전용**입니다(조직이 곧 구역 범위의 경계라서 역할별 위임은 아직 없음). 구역과 연동된 조직(`d1`~`d3`)은 이름 변경·삭제·보관이 막혀 있습니다.
- **구역·반 목표 화면**: 기간(월간·주간·직접)·구역·반·단계별 목표 저장/수정/삭제, 단계 이력으로 계산한 달성·부족·달성률, 엑셀 내보내기. 비관리자는 배정 구역의 목표만 다루고, 구역 없는 반 목표는 관리자만 다룹니다.
- **대상자 ↔ 작업 영역**: 대상자 등록·수정은 4.0.41 검증을 거치며, 웹 화면에 없는 기존 정보(인도자·활동·단계일 등)는 수정 때 보존합니다. 단계를 바꾸면 실제 변경 시각으로 단계 이동 이력이, 모든 변경에는 변경 이력이 남습니다. 데모 자료에는 가상 단계 이력과 목표가 들어 있습니다.
- **접근 권한**: 새 화면은 비관리자 기본값이 "접근 없음"입니다(기존 대시보드·대상자 기본값은 유지). 접근 권한 관리에서 역할별로 켜며, 화면에 없는 동작(예: 통계 화면의 쓰기)은 켤 수 없습니다. 메뉴는 묶음 제목 아래에 표시되고, 길면 메뉴만 따로 스크롤됩니다.
- **엑셀 업로드 라우트**: 라우트에 `binary: true`(POST만)를 주면 `app.js`가 로그인·권한을 먼저 확인한 뒤 XLSX를 Buffer로 받아 `ctx.body`(= `ctx.file`)에 넘깁니다. 같은 출처, `Content-Type`이 xlsx 또는 `application/octet-stream`, 최대 8 MiB(`maxBytes`로 더 줄일 수 있음), ZIP 서명 확인. 일반 JSON 요청은 64 KiB 상한이며, 긴 붙여넣기를 받는 고정 경로 세 곳(`POST /api/daily/convert`, `POST /api/daily/notice`, `POST /api/calling/report/preview`)만 1280 KiB까지 받습니다. 브라우저는 `postXlsx(url, file)`(또는 각 화면 모듈의 업로드 도우미)을 씁니다.
- **미리보기**: 가져오기처럼 나중에 적용하는 작업은 `putPreview`/`takePreview`로 사용자·구역 범위·만료(15분)·자료 버전에 묶어 서버 메모리에 보관합니다.

## 이관 대기·알려진 차이 (이 단계에 없음)

완전한 기능 일치나 운영 준비 상태가 아닙니다. 확인된 차이는 다음과 같습니다.

- 분석 화면의 기존 일부 필터와 표 열 설정(열 선택·순서·너비 저장)은 아직 옮기지 않았습니다.
- 기존 앱의 자료실 생성·전환·관리, 네이티브 보관함, `.cddshare` 공유파일은 웹 이관 범위에서 제외했습니다. 공유와 접근 관리는 이후 중앙 DB와 사용자·구역별 권한으로 처리합니다.
- 누적 엑셀 반영은 가상 자료로만 대조했고, 실제 누적 파일과의 일치는 확인하지 않았습니다.
- 공통코드 엑셀은 관리 화면에서 내려받기와 가져오기(미리보기 후 반영, `/api/admin/codes/export`·`import/preview`·`import/apply`)가 연결되어 있습니다. 남은 차이: 별칭 직접 편집·삭제 없음, 사용 여부 표시 없음(삭제 시 서버가 사용 중 여부를 알려 줌).
- 구성원 연락처, 그 밖에 이 문서에 적히지 않은 기존 기능은 아직 이관하지 않았습니다. 기존 앱 기능과 화면별로 일치하는지는 가상 자료로만 대조했습니다.
- 조직·구성원 비고처럼 자유 문장에 들어간 전화번호 모양의 값은 서버가 끝 네 자리만 남기고 가립니다(화면·엑셀 동일). 화면에서 가려진 그대로 저장하면 기존 값을 유지합니다.
- 대상자 등록·수정은 인도자 지정(같은 구역의 활동 중 구성원)과 사용자 정의 항목(관리 화면에서 만든 문자·숫자·날짜·선택·체크 항목)을 다룹니다. 사용자 항목은 `custom` 객체로 받아 설정에 있는 항목만 허용하고 4.0.41 `M.validatePerson`이 값을 검증하며, 수정할 때 요청에 없는 항목은 기존 값을 유지합니다. 연락처로 지정된 항목(이름이 휴대폰·연락처·전화 등)은 값을 바꿀 수 없고 끝 네 자리만 보이며, 전화번호 모양의 문자열은 사용자 항목에 저장하지 않습니다. 대상자 연락처 자체는 이 화면에서 입력하지 않습니다. 구역 이름과 맞지 않는 `region`의 대상자는 관리자 화면에도 나타나지 않습니다.
- 연락처는 암호화 저장 설계 전까지 이 경로로 저장하지 않으며(저장 시 제거, 조회는 끝 네 자리), 여백 신청, 관계형 DB, 실제 자료 이관, 운영 배포는 별도 작업입니다.
